# 历史会话修复等待活动 Provider Sync

## 背景

CCP 启动 Codex 时可以自动执行 Provider Sync，用户也可以在“会话与记忆”页面手动点击“修复历史会话”。两条路径共享 `~/.codex/tmp/provider-sync.lock`，用于避免并发写入 rollout 和 SQLite。

当前陈旧锁可以自动回收，但仍在运行的后台同步会留下有效的新鲜锁。手动修复遇到该锁时立即返回失败，用户只能等待后再次点击。实际日志中第一次点击因锁失败，约 37 秒后第二次点击成功，说明这是可恢复的正常竞争，不应作为即时失败暴露给用户。

## 目标

- 保留单写者锁，禁止两个 Provider Sync 同时修改会话数据。
- 手动修复遇到有效锁时，在有限时长内等待锁释放并自动继续。
- 等待期间保留前端“正在修复”状态，不要求用户再次点击。
- 锁在等待上限内释放时，按正常成功路径返回，并只触发一次后续 Codex 重启。
- 锁持续超过等待上限时，返回明确失败，不删除或覆盖有效锁，不执行部分同步。

## 非目标

- 不改变启动器自动同步遇到有效锁时的快速跳过行为。
- 不改变陈旧锁判断、会话筛选、SQLite 更新、rollout 重写、备份或回滚语义。
- 不直接删除用户现有锁目录，不修改真实会话或 API 凭据。
- 不允许手动修复无限等待。

## 功能要求

- 数据层提供显式的“等待锁后同步”入口，普通 `run_provider_sync` 与 `run_provider_sync_with_target` 保持现有快速返回契约。
- 等待入口使用单调时钟和短间隔轮询；每次获得锁时仍复用原子目录锁与陈旧锁恢复逻辑。
- 手动 Tauri 命令使用等待入口；启动器继续使用快速返回入口。
- 等待上限和轮询间隔必须集中定义，并允许测试注入较短时长，避免慢测试。
- 只有锁竞争可以等待；配置错误、文件错误和其他 `Skipped` 原因必须立即返回。
- 等待成功或超时都不得泄露会话内容、Provider Key 或其他凭据。

## UI 与交互要求

- 点击“修复历史会话”后立即显示现有运行中通知。
- 后台同步释放锁后，手动修复自动完成，显示一次成功通知并执行一次 Codex 重启。
- 超时时显示锁仍被占用的真实原因，不显示伪成功，也不重启 Codex。

## 交付范围

- Provider Sync 有界等待实现与单元/集成回归测试。
- Manager 手动修复命令接入等待入口。
- 对应验收标准和 Release 构建。
