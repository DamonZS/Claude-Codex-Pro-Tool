# Manager Liquid Glass 外壳落地

## 背景

CCP Manager 已完成信息架构重构，并已有一份用户确认的 Liquid Glass 交互效果稿。当前代码已经具备浅色、深色、跟随系统、侧栏折叠、顶部命令栏和完整更新下载链路，但真实应用仍使用旧的高不透明度深色视觉层，浅色模式也存在局部对比度与材质不一致问题。

## 目标

- 将已确认效果稿的高密度 Liquid Glass 视觉语言落地到真实 Manager。
- 保留现有 React 状态、路由、Tauri IPC、业务组件和数据位置。
- 侧栏展开宽度收窄到 200-216px，折叠宽度为 56px，并保留本地持久化与 Tooltip。
- 顶部上下文控件按“Agent 筛选、搜索、当前供应商”连续靠左排列，三个启动操作保持在右侧；Agent 筛选只提供 Codex 与 Claude，默认选中 Codex。当前供应商使用“代理健康红绿状态点 + 供应商名 + 当前 + 下箭头”的紧凑一体控件，不再重复展示独立代理状态；控件可展开并使用现有供应商切换动作。供应商超过浮层可用高度时，中间列表独立滚动，标题与“管理供应商”操作保持可见。
- Liquid Glass 材质覆盖全部一级路由和业务页面，而不是只覆盖概览；浅色供应商编辑器需要有可辨识的玻璃外壳、区块边界和控件边框，复杂表单字段、日志和长文本仍保持高不透明度。
- 在“启动/重启 Codex”之前增加条件式更新入口，复用真实检查、下载、进度和安装流程。
- 在 960x640、1280x800、1440x900、1920x1080 与 3840x2160 高 DPI 场景保持清晰稳定。

## 非目标

- 不重写 `App.tsx` 的状态与路由中枢。
- 不新增或修改更新后端协议、下载地址、安装方式与发布流程。
- 不修改供应商协议、代理、会话、记忆、提示词、扩展和 Codex Renderer 注入行为。
- 不增加 npm 依赖，不修改 Codex/Claude 注入脚本。

## 用户视角

- 用户可在左侧展开或折叠一级导航，选择会跨会话保留。
- 深色模式呈现高透明度黑玻璃外壳，浅色模式呈现高对比度的明亮磨砂玻璃；正文、表单、日志仍保持足够高的不透明度。
- 用户可在主题中心直接选择不低于 1920x1080 的本地 PNG、JPEG 或 WebP 作为 Manager 背景，无需手工编辑主题包；选择后立即预览并跨重启保留，也可恢复主题自带或内置背景。
- 检测到新版本时，顶部出现无背景框的亮绿色粗体下载箭头。悬停可查看当前版本、最新版本和更新说明；点击后可看到真实下载阶段与进度。
- 未检测到更新、检查失败或已是最新版本时，顶部不显示误导性的下载箭头。

## 功能要求

1. Manager 首次加载后静默调用一次现有 `check_update`，不得阻塞首屏或触发成功通知。
2. 顶部更新入口只在 `updateInfo.updateAvailable === true` 时渲染。
3. 更新入口位于“启动/重启 Codex”之前；图标无矩形底框，使用亮绿色和约 3px 描边。
4. 悬浮层显示当前版本、最新版本、更新说明及当前下载状态；长说明可换行或截断，不覆盖顶部其他操作。
5. 点击入口调用现有 `performUpdate(updateInfoToRelease(updateInfo))`，并使用 `update-download-progress` 产生的真实阶段、百分比和字节数。
6. 下载期间入口不可重复触发，并通过文字和 `aria-live` 表达状态。
7. 侧栏继续使用现有 `localStorage` 状态，不改变导航项、路由和外部导航事件。
8. 当前 Codex 主题包可通过 `asset_variables` 声明 Manager 的高清环境背景；优先读取 `--ccp-theme-manager-background`，未声明时兼容复用 `--ccp-theme-art`。
9. Manager 只读取主题系统已经校验并编译出的 PNG、JPEG 或 WebP data URI，不加载远程 URL，不执行主题的 Renderer CSS、根类或根属性。
10. 默认主题、主题未声明背景或背景读取失败时，继续使用 Manager 内置的深浅色背景图，不显示损坏图片或上一主题的陈旧背景。
11. 应用主题、恢复默认主题或替换当前主题成功后，Manager 背景立即刷新；Codex 主题本身仍按现有规则在重启 Codex 后生效。
12. 主题包仍受单文件 8 MB、总包 32 MB 和运行时资源上限约束；背景最低为 1920x1080，4K 图片推荐使用经过压缩的 WebP 或 JPEG。
13. 主题中心提供明确的“设置背景”入口，选择文件后由 Core 校验真实图片格式、最低 1920x1080 尺寸和大小；用户选择的背景优先级高于主题包变量。
14. 用户选择的 Manager 背景只写入 CCP 主题状态目录，不修改源图片、Codex 安装文件、主题 Renderer CSS 或用户供应商配置。
15. 直接设置背景使用临时校验和原子写入，最多保留一份上一背景；写入或状态提交失败时继续使用上一可用背景。
16. 主题中心提供“恢复主题背景”操作，清除用户背景后依次回退到 `--ccp-theme-manager-background`、`--ccp-theme-art` 和内置深浅色背景。

## UI 与视觉要求

- 外壳采用克制的环境色、半透明表面、18-30px 模糊、细描边和内高光；侧栏与顶栏必须能辨认背景明暗和轮廓，禁止用过强模糊重新变成不透光黑块。
- 深色以中性黑灰为主，浅色以冷白灰为主，绿色仅用于更新、健康和选中等有限状态。
- 页面外壳、侧栏、顶部栏、命令面板和 Toast 可使用玻璃材质；表格、表单、日志和长文本使用 94%-100% 不透明表面。
- 所有文字 `letter-spacing: 0`，Windows 使用 Segoe UI，macOS 使用系统字体；代码、路径和日志继续使用等宽字体。
- 控件圆角 6px，面板不超过 8px；动效 140-220ms，并尊重 `prefers-reduced-motion`。
- 浅色模式不得在正文文字上叠加噪点或降低清晰度，正文与表面达到 WCAG AA 可读对比度。
- 顶部“Claude 一键汉化”和供应商“测试连接”使用成功绿色，普通导航、编辑和启动动作保持中性色或系统蓝，不能混淆动作语义。
- 高清背景不做放大 transform，SVG 图标保持矢量渲染；在 3840x2160 下不把工作区限制为中央小窗口，也不使用低分辨率装饰层覆盖背景。

## 技术约束

- 保留 `ops-shell`、`ops-rail`、`ops-workspace`、`ops-topbar`、`ops-screen` 类名。
- 复用 `UpdateResult`、`updateInfoToRelease`、`updateProgressLabel`、`formatDownloadBytes` 和现有 actions。
- 使用现有 Lucide 图标；不新增依赖。
- 优先通过 `styles.css` 末尾覆盖层收敛视觉，避免破坏旧业务组件选择器。
- 保留只读 Tauri 命令 `load_codex_theme_background`，并新增 `set_codex_manager_background` 与 `clear_codex_manager_background`。三者只处理本地图片、主题 ID、尺寸、来源和 data URI，不返回或执行主题 CSS。
- 自定义主题背景通过 `AppShell` 内专用的真实 `<img>` 背景层渲染，使用与主题中心预览一致的已校验 data URI；存在自定义背景时隐藏内置背景伪元素，不存在时自动回退到内置深浅色资源。不得依赖把大型 data URI 塞入 CSS 自定义属性。
- 概览“请求与事件时间线”的标题说明、图例、泳道标签、时间刻度、事件名称、事件时间和空态在常用桌面尺寸下均使用可读字号；时间线不使用 7-9px 字体模拟高密度或高分辨率。

## 交付范围

- `AppShell.tsx`：真实更新入口、进度浮层及现有侧栏交互的视觉语义。
- `App.tsx`：向外壳传递真实更新状态、主题背景和动作，并执行一次非阻塞静默检查。
- `styles.css`：Liquid Glass Token、浅深主题、响应式与高 DPI 视觉层。
- `codex_theme.rs`、Manager Tauri 命令与前端类型：安全提取并传递当前主题背景。
- `CodexThemeCenterScreen.tsx`：展示当前 Manager 背景、1080p 及以上图片选择和恢复入口。
- `Theme/README.md`：记录主题包 Manager 背景变量、最低尺寸、格式和大小约束。
- 对应验收文档、类型检查、前端构建、Rust 测试、默认 Release 构建和真实界面截图。

## 概览控制台结构

概览页不是旧状态卡片的换肤。它必须按已确认参考图重组为高密度运维控制台，并继续使用真实 Manager 状态：

1. 顶部四项 KPI 展示供应商数量、本地代理状态、Codex 增强状态和盘古记忆条目数。无法从当前状态证明的数据必须显示“未检测”或“暂无”，不得伪造延迟、成功率、请求量或注入百分比。
2. 主工作区采用“供应商路由列表 + 当前请求链路拓扑 + 智能诊断 Inspector”三栏结构。窄屏可按顺序堆叠，但不得丢失任何操作。
3. 供应商列表直接读取 `BackendSettings.relayProfiles`，只支持 Codex、Claude 两种范围筛选并默认选择 Codex，不保留“全部”或不可见的全量状态；当前配置、路由状态和缺少凭据必须用文字加状态点表达。
4. 中央拓扑按所选供应商显示“供应商 -> 协议/本地代理 -> 目标 Agent”，模型、协议、目标应用、代理在线状态均来自现有配置与概览结果。
5. Inspector 展示所选供应商的模型、协议、目标、路由、凭据遮罩和已知运行状态，并保留编辑配置、设为当前、测试连接、刷新及现有修复动作。
6. 测试连接必须调用已有 `test_relay_profile` 可达性测试，不得用获取模型代替连接测试。
7. 底部时间线只读取脱敏后的现有诊断日志及已有时间戳状态。界面不得展示 API Key、Token、完整 URL、原始请求正文或私密会话；没有可展示事件时提供真实空态。
8. 旧概览中的公告入口、记忆开关、Claude 开发模式和修复能力必须保留，但可迁移到 Inspector 或紧凑操作区，不能继续占用巨型低密度卡片。
